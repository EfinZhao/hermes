# Golden packets

The answer key for the packet format. Firmware and receivers must produce and read exactly these bytes.
Generated by `tools/make_golden.py` from `messaging/msgcodec.py`; do not edit by hand.

| File | Contents |
|---|---|
| `data.json`, `raw_can.json`, `config.json`, `ack.json` | Valid packets of each message type |
| `crc32.json` | CRC-32 (IEEE) test vectors, including `"123456789"` = `0xcbf43926` |
| `invalid.json` | Packets a decoder must reject, with the reason |

## Case kinds
- `encode`: one packet built from `params` (header values) and `records`. An encoder given these must output `packets[0].hex`.
- `packetize`: `items` (samples with absolute times) fed to a packetizer with `params`
  (`max_packet_bytes`, `start_seq`, `flags`) must give exactly `packets`, in order. Items are sorted by time (equal times keep their order), split to fit, and `base_ms` is the first record's time.
- `crc32`: `crc32` is the CRC-32 of the bytes in `input_hex`.
- `invalid`: a decoder must reject `hex`. `error` is one of `too_short`, `bad_magic`, `unsupported_format_version`, `length_mismatch`, `crc_mismatch`, `record_count_mismatch`.

## Fields
- `hex`: the whole packet (header, records, CRC) as lowercase hex. A decoder must give back `header` and `records`.
- Floats are float32. Compare `value_bits` (the exact bit pattern), not `value`; `value` is `null` for NaN and infinity.
- `can_id` is a hex string; bit 31 set means a 29-bit id (`extended` says so).
- Everything is little-endian. See the packet format table in the project docs.
